TITLE: lxml iterparse mode for speed
AUTHOR: Kurt
DATE: 10.21.2007 12:37
DESC: faster and faster
-----
BODY:
Using an lxml etree to walk a tree of 100k objects is decidedly a bad
idea.  It chews up a huge amount of memory and takes forever to get
the tree loaded (after 15 minutes, I stopped checking).  I am moving
some of my code to the iterparse style of handling XML which is
several order of magnitude faster.  By controlling what tags get trees
built, it runs in less than a second now.  Here is a tiny.rksml
example of the xml source:

And here is the code that can quickly walk the parts of the tree that I need:
<pre>
<font color="#444444">#!/usr/bin/env python</font>
<strong>from</strong> <font color="#2040a0">lxml</font> <strong>import</strong> <font color="#2040a0">etree</font>
<strong>for</strong> <font color="#2040a0">event</font>,<font color="#2040a0">element</font> <strong>in</strong> <font color="#2040a0">etree</font>.<font color="#2040a0">iterparse</font><font color="4444FF">(</font><font color="#008000">'tiny.rksml'</font>,<font color="#2040a0">tag</font><font color="4444FF">=</font><font color="#008000">'Knot'</font><font color="4444FF">)</font><font color="4444FF">:</font>
    <strong>print</strong> <font color="#2040a0">event</font>, <font color="#2040a0">etree</font>.<font color="#2040a0">tostring</font><font color="4444FF">(</font><font color="#2040a0">element</font><font color="4444FF">)</font>
</pre>
And the resulting output:
<pre>
./iterparse.py
end &lt;Knot Name="SHOULDER_AZ" Units="RADIANS"&gt;-0.619&lt;/Knot&gt;
end &lt;Knot Name="SHOULDER_EL" Units="RADIANS"&gt;-0.1231&lt;/Knot&gt;
</pre>
For my actual program, this does require me to do a lot more book
keeping.  There is no peaking backwards or upwards of the current element
unless I cache what I need.
