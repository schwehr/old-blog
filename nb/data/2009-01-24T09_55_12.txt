SEG-Y is a really common format, but it is almost the UN-format.  It
really seems to only be a hint.  Everybody seems to write it slightly
differently.  I hit this in the past and even wrote a paper on it:

[<a href="http://vislab-ccom.unh.edu/~schwehr/papers/schwehr2008-pythonpapers-seismic-py.pdf">PDF</a>] Schwehr, seismic-py: Reading seismic data with Python., The Python Papers, 3:2, 8 pages, Sep 4, 2008.

I'm in the process of rewriting segy-py/seismic-py and calling it
simplesegy.  This new library is only meant to handle the low level
parsing with minimal logic and preferably no support for things like
header math.  BTW, I think header math is a bad thing... use a
separate database to prevent polution of the original segy.

One feature I do want to get right is being able to return the
location/position of traces/shots.  With the Driscoll <a href="http://www.edgetech.com/">EdgeTech</a> Chirp
system, I had it right.  Just divide the raw values by 3600.0 and I
had the position...
<pre>    def position_geographic(self):
        return self.hdr['X'] / 3600., self.hdr['Y']/ 3600.</pre>
This gives:
<pre>Position Raw: (-422142, 118406)
Position:     (-117.26166666666667, 32.890555555555558)</pre>
For this current rewrite, the goal is to be able to do templated 
metadata generation of UN Law of the Sea <a href="http://www.knudsenengineering.com/">Knudsen</a> chirp data.
When I try the same thing, I get:
<pre>Position Raw: (513074681, 52682969)
Position?     (142520.74472222221, 14634.158055555556)</pre>
I know that 142&deg;E,14&deg;N is the right neck of the woods, but
the format does not contain any info about how the position is
represented.  Neither the EdgeTech or Knudsen has anything that 
says how I am supposed to interpret the coordinates... neither has
an <i>Extended Textual Stanza</i> (See Rev 1 Appendix D).  To be
fair, the Knudsen reports it is SEG-Y Rev 0, but still.

From the <a href="http://www.knudsenengineering.com/files/manuals/320BUserManual.pdf">Knudsen 320BR chirp manual</a>: 
<pre><b>7.3.4.6 SEG-Y Extended Data Fields</b>
The original SEG-Y specification does not account for many useful data
fields. If the user selects the option to include the extended data
fields, numerous operation controls are recorded in the unassigned
bytes at the end of the Rev0 Trace header. Some SEG-Y readers do not
recognize files that contain data in these bytes so it is advisable to
verify the requirements for the desired reader application before
selecting this option.</pre>
