default Apple configuration.  I am giving NTP a whole bunch of servers
to choose from.  NTP works best when it has at least 3 servers to pick
from.  I am using servers from the <a

Remote is the host name that ntp is talking to.  refid is the host
that is the "parent" of the remote host.  NTP works like a tree
propagating time from host to host.  The "st" denotes the stratum or
distance from a true time source (e.g. a GPS, cell phone, or other
radio signal).  A computer attached to a time source is <b>stratum
1</b>.  "t" is the type of connection that the remote has:
<pre>u: unicast or manycast client
b: broadcast or multicast client
l: local (reference clock)
s: symmetric (peer)
A: manycast server
B: broadcast server
M: multicast server</pre>
<i>When</i> says how long it has been since ntpd has talked to the
remote ntp server.  <i>Pool</i> is how the time between talking to
this remote server. <i>reach</i> is an set of flags that I have not
looked into.  <i>Delay</i> is the number of milliseconds roundtrip
from the remote to the root server (stratum 1) and back.
<i>Offset</i> is estimated different in time in milliseconds from that
host to the root clock that it is synced to.  <i>Jitter</i> is how
much time varies in milliseconds between several time queries for that host.

Sometimes you hit a stratum 1 server in the ntp pool.  There are a
number of fields in the refid depending on which time source is being
used, but here is one I happend apon:
<pre>     remote           refid      st t when poll reach   delay   offset  jitter
==============================================================================
*207.171.30.106  .PPS.            1 u 1283  68m   37   83.255    3.331   0.251</pre>
If you want to trace up the stratum levels for your computer, you can use <a href="http://www.eecis.udel.edu/~ntp/ntp_spool/html/ntptrace.html">ntptrace</a>:
<pre><b>ntptrace</b>
localhost: stratum 3, offset -0.005283, synch distance 0.403253
17.151.16.22: timed out, nothing received
***Request timed out</pre>
However, as you can see here, not all hosts respond to the trace
requests.  To give a view of what a successful trace looks like, I've

<pre><b>ntptrace  72.18.205.157</b>

The next command to try is <a
href="http://www.eecis.udel.edu/~ntp/ntp_spool/html/ntpdc.html">ntpdc</a>
- the "special query program".  There are two key command to use here
to monitor how well NTP is doing.  I am still learning how to
interpret these values.

The sysinfo command to ntpdc is the real meat of monitoring ntp:

The loopinfo is also important and has the offset which is the
estimate of how far off of the reference clock we are.  But note, if
you drop back to the local clock, time will be right on, but the local
oscillator in your computer is horrible at keeping time.
<pre><b>ntpdc -c loopinfo</b>
offset:               -0.013710 s
frequency:            -3.706 ppm
poll adjust:          30
watchdog timer:       173 s</pre>
That is the basics of looking at ntp with commands.  You can also
enable logging in the ntp.conf file and plot out values over time.

When working with data, I always keep everything in UTC.  In python, the easiest way to timestamp 
data is by calling <i>time.time()</i>, which returns a UNIX UTC timestamp number and datetime can help
too:
<pre><b>ipython</b>
import time, datetime, calendar
timestamp = time.time()
# 1270332482.344033
datetime.datetime.utcfromtimestamp(1270332482.344033)
# datetime.datetime(2010, 4, 3, 22, 8, 2, 344033)
datetime.datetime.utcnow()
# datetime.datetime(2010, 4, 3, 22, 9, 36, 132771)
calendar.timegm(datetime.datetime.utctimetuple(datetime.datetime.utcnow()))
# 1270332678</pre>
