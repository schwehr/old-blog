UPDATE 2010-Jul-06: <a
href="http://code.google.com/apis/kml/documentation/extendeddata.html">KML's
ExtendedData</a> is basically what I was looking for with KML and <a
href="http://sgillies.net/">Sean Gillies</a> pointed me to <a
href="http://sgillies.net/blog/1018/geographic-odata/">his example</a>
of Microsoft's <a href="http://www.odata.org/">Open Data Protocol
(OData)</a>.  Sean points out that Google Maps does not understand
OData.  GeoRSS needs to pull in something like one of these.

We have started working with GeoRSS fields and my frustration with
GeoRSS continues.  I posted back in March asking for thoughts on
GeoRSS: <a
href="http://schwehr.blogspot.com/2010/03/sensor-data-in-georss.html">Sensor
data in GeoRSS?</a>.  I got some helpful thoughts from Sean Gillies,
but have not heard from any others.

Here is an example of my USCGC Healy feed of science data that is only in HTML table form within the description:

<a href="http://maps.google.com/maps?q=http:%2F%2Fvislab-ccom.unh.edu%2F~schwehr%2Fhealy%2Fhealy-science-google.rss">Healy Science feed in Google Maps</a>

<img title="My use of XML tables for data in RSS feeds" withgrayborder="True" src="http://schwehr.org/blog/attachments/2010-07/healy-rss-feed.png"/>

It's got some really nice features that include:
<ul>
<li>Being pretty simple (when compared to SensorML and <a href="http://www.opengeospatial.org/standards/sos">SOS</a>)</li>
<li>You can just throw a URL in Google Maps and see the data</li>
<li>It works inside normal RSS readers (e.g. my USCGC Healy Feeds)</li>
<li>It's a simple file that you can copy from machine to machine or email.</li>
<li>It should be easy to parse</li>
<li>Points and lines work great</a>
</ul>
The trouble comes with:
<ul>
<li>Validation is a pain, but appears to be getting better</li>
<li>What should you put in the title and description?</li>
<li>It seams you have to create separate <i>item</i> tags for points and lines for things like ships</li>
<li>There is no standard for machine readable content other than the location</li>
</ul>

This is how the AIS feed looks in Google Maps... mostly enough to see
what is going on.  If you know the name of a vessel, you can find it
on the left side list of ships.  That's a great start, but it is hard
to take that info into a database.  If the fields change at all in the
title or description, all parsers that use that feed MUST be
rewritten.

There are some problems in the sample above.  First, the description
doesn't contain a human readable version.  This causes the GoogleMaps
display to give us nothing more than the current position of this
"buoy" (and a recent track history that comes as a separate entry).
Ouch.  That's hard to preview.  Second, the machine readable portion
is fine, but I can't write anything that can discover additional data
fields if they are added.  If someone adds
&lt;foo&gt;1234&lt;/foo&gt;, is that field a part of something else or
is it more sensor data that I should be tracking?  A namespace for
sensor data would help.  Then I could pick off all of the fields that
are in the "SimpleSensorData" namespace.  But, I have to say that
namespaces are good, but a pain.  I would prefer a <b>data</b> block,
where everything in there is a data field.  It would also be good to
separate units from the values.  Here is how it might look:

There was also an assertion that KML would be better.  However, I
would argue against KML as a primary data transport mechanism.  KML is
a presentation description, not a data encoding format.  It's much
like when I ask someone for an image and they take a perfectly good
JPG, TIF, or PNG and put it in a PowerPoint... sending me only a
PowerPoint.  That can be useful, especially if there are annotations
they want on a final, but I must have the original image or a lot is
lost.
